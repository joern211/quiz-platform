# N3 — Private Reihenfolgeantworten, technische Grundlage: Design

Base: `main` @ `b38df2bb665dc77c5a29d18156251046a31e1967` (N2 inkl. R1/R2 gemergt, PR #31). Branch `feature/n3-ordering-foundation`, direkt von `main`.
Status: **N3-Vorbereitung implementiert und geprüft; noch kein produktiver Sortier-Verbraucher, vollständige Core-DoD offen** (Master §13.2 verlangt zwei echte Game Engines; keine existiert).

## 1. Scope und ausdrückliche Grenze

Geliefert: Vertrag für eine private Reihenfolgeabgabe (öffentliche Itemmetadaten, vollständige Permutation stabiler IDs, serverseitige Referenz als geordnete Äquivalenzgruppen), deterministischer Positionsvergleich (Fakten, keine Punkte), serverseitiger Abgabe-/Lock-/Vergleichsbaustein mit Projektion, Midnight-Komponente `OrderingForm`, Tests, Integrationsanleitung. Zusätzlich die kleine N1-Anzeigekorrektur (§8).

Nicht geliefert (absichtlich): keine Timeline-/Higher-or-Lower-Engine, keine Katalogfreischaltung, keine Spiel-/Testroute, kein `sort.update`/`sort.lock`/`ordering:submit`, keine persistierten Entwürfe/Teilabgaben, kein Bieten/Voting/Würfeln, kein Content-/Editor-System, keine Datums-/BC-/Zeitzonen-/Gleitkomma-Normalisierung, keine Punktformel/Bonus/Zeitwertung/Team-Aggregat/Siegentscheidung, keine Umdeutung bestehender Spiele, kein generischer Formular-Designer, kein Drag & Drop. Bestandsengines und `SubmissionRecord` unverändert.

Quellen: Arbeitsauftrag N3 (01.11.2026); Master §§2, 4.15, 5.5, 5.7–5.9, 5.13–5.24, 5.26–5.36, 6.3/6.10/6.11, 10, 12, 13.2, 14, 15.8; `docs/specs/pr12/games/timeline.md`, `decision-register.md` (DEC-TIM-01: nur Vorschlag); N1/N2-Dokumente einschließlich R1/R2.

## 2. Vertrag (`@quiz/shared/ordering`)

Subpath-Export `@quiz/shared/ordering` (`packages/shared/src/ordering.ts`); der shared-Index bleibt unverändert. Strip-only-fähiges TypeScript, **eigenständige Datei** (keine relativen Imports: Node im Strip-only-Modus löst `./x.js` nicht auf `.ts` auf). Die Anzeige-Textpolicy ist deshalb aus N2 dupliziert; ein Paritätstest (`ordering.test.ts`) hält beide zusammen.

**Drei strikt getrennte Dinge.**
A) *Öffentlich:* `OrderingConfig` — Item-IDs, Labels, Hilfen, **Präsentationsreihenfolge**. B) *Privat je Teilnehmer:* die abgegebene Reihenfolge. C) *Privat serverseitig:* Referenz (geordnete Äquivalenzgruppen) und daraus abgeleitete Vergleichsfakten.

**Konfiguration (A).** `{ schemaVersion: 1, prompt: string|null, directionHint: string|null, items: [{ itemId, label, help: string|null }, …] }`, streng (`.strict()`): kein Platz für Sortierwert, Jahr, Datum, `canonicalIndex`, `tieGroup`, Lösung, Referenz oder Seed — auch nicht auf Item-Ebene (getestet). Die Reihenfolge von `items` ist die **Startanzeige**, die der Aufrufer/serverseitige Snapshot liefert; sie sagt nichts über die richtige Reihenfolge. `prompt`/`directionHint` sind reiner Anzeigetext; nichts wird daraus abgeleitet.
Schutzgrenzen (keine Spielregeln): 2–12 Items (zwei ist die kleinste Liste mit Ordnungsinformation; 12 hält die Liste auf dem Handy bedienbar), ID ≤ 40 (`^[a-z][a-z0-9_-]*$`, reservierte Namen `constructor`/`prototype`/`proto` und `__proto__` abgelehnt), Label ≤ 120, Hilfe ≤ 200, Aufgabe ≤ 200, Richtungstext ≤ 80, Revision ≤ 80. Damit ist die gesamte öffentliche Config rechnerisch < 5 KB; die PR12-Defaults (5 bzw. 4–7 Items) sind **nicht** hartcodiert. Texte: dieselbe Policy wie N2 (kein Rand-Whitespace, keine Steuer-/Bidi-Zeichen, keine einzelnen Surrogate) plus „nicht unsichtbar“ (ein Item ohne sichtbares Label wäre unbedienbar). Gleiche Labels bei verschiedenen IDs sind erlaubt.
Wichtig für spätere Aufrufer: Item-IDs sind öffentlich. **Opake, nicht wertcodierte IDs verwenden** (nicht `y1969`) und die Startreihenfolge getrennt von der Lösung erzeugen (nicht versehentlich korrekt sortiert). Ein Parser kann semantisch nicht jede unglücklich benannte ID erkennen; das ist Aufruferpflicht.

**Identität.** `orderingConfigKey(config)` = Schemaversion + Item-IDs **in Präsentationsreihenfolge** (Labels/Hilfen/Texte ausgenommen). Er pinnt den Serverscope: eine nach einem Rejoin neu gemischte Startreihenfolge ist ein *anderer* Scope und wird abgewiesen (Master §5.16/§6.11: nie neu mischen). `orderingItemSetKey(config)` = Schemaversion + **sortierte** IDs (reihenfolgeunabhängig) — nur für die UI, die einen Entwurf über eine bloße Metadaten-Umordnung derselben IDs behält. Beide enthalten nur öffentliche Daten, nie etwas von der Referenz.

**Abgabe (B).** `{ schemaVersion: 1, itemIds: [id, …] }` — Array stabiler IDs, kein Trennzeichenstring, keine Labels, keine Indizes. Gültig ist genau eine **vollständige Permutation** der konfigurierten Items (`validateOrdering`): jede ID genau einmal; fehlend → `ORDER_MISSING_ITEM`, unbekannt/fremd/zu lang → `ORDER_UNKNOWN_ITEM`, doppelt → `ORDER_DUPLICATE_ITEM`, falscher Typ → `ORDER_WRONG_TYPE`, falsche Version/Zusatzschlüssel (auch eigener `__proto__`-Schlüssel)/Nicht-Plain-Objekt → `ORDER_MALFORMED`. Nichts wird sortiert, entdoppelt, entfernt oder aufgefüllt; die Reihenfolge des Aufrufers bleibt wörtlich. Eine Liste mit der richtigen Länge, aber falscher Menge (`[a, a, c]`) ist ungültig (kein Längenvergleich). Eine leere/partielle Liste ist nie eine Abgabe. Die Länge wird **vor** jeder Iteration begrenzt (> 12 → `ORDER_MALFORMED`); es gibt keine n×n- oder n!-Berechnung. Issues tragen nur *konfigurierte* IDs oder `null` — nie einen Angreifer-String. Das Ergebnis ist ein frisches Objekt (keine Aliase zur Eingabe).

**Referenz (C).** `OrderingReference = { schemaVersion: 1, revision, groups: string[][] }` — **geordnete Äquivalenzgruppen** (Strict-Fall: eine ID je Gruppe; Hilfsfunktion `strictOrderingReference`). Gruppe *g* belegt den zusammenhängenden Positionsbereich ihrer Größe hinter allen früheren Gruppen: `[[a,b],[c]]` erlaubt `a,b,c` und `b,a,c`, **nicht** `c,a,b`. `validateOrderingReference(config, raw)`: jede konfigurierte ID genau einmal über alle nichtleeren Gruppen; leere/überlappende Gruppen, fehlende/fremde IDs, Zusatzschlüssel, falsche Version → `ORDERING_REFERENCE_INVALID` mit Issues (`REFERENCE_*`). Überlappende Alternativen sind nicht ausdrückbar; nichts wird aufgezählt. `revision` ist ein **opakes** Label der serverseitigen Content-Revision (`^[A-Za-z0-9][A-Za-z0-9._:@-]*$`, ≤ 80); sie darf die Ordnung nicht kodieren (sie wird im Zustand gepinnt und nach dem Reveal gezeigt). **N3 leitet Gleichwertigkeit nie aus Labels, IDs, Normalisierung oder Zahlen ab** und bestätigt weder DEC-TIM-01 noch `TOLERATED_TIES`; ob gleiche Jahre eine Gruppe bilden, entscheidet eine spätere Engine nach Nutzerfreigabe. Auf-/absteigend entsteht ausschließlich durch die Referenzaufbereitung der Engine — es gibt keine versteckte Umkehrung und keine Label-/ID-Sortierung im Comparator.

**Vergleich (`compareOrdering`, Vertrag `ORDERING_POSITION_MATCH_V1`).** Reine Integer-Rechnung über ≤ 12 Einträge; validiert beide Eingaben selbst (ein Ergebnis beruht nie auf einer Behauptung des Aufrufers). Ergebnis: `{ contract, referenceRevision, itemCount, matchedPositions, complete, positions: [{ position (1-basiert), itemId, matches }] }`. `matches` ⇔ das Item steht im Positionsbereich seiner Gruppe; `complete` ⇔ alle Positionen passen. Das sind **Fakten**: keine Punkte, kein Gewinner, keine Aussage zur Teilwertung. Deterministisch: identische Eingaben → identisches Ergebnis, unabhängig von Uhr, Objektidentität, Einfügereihenfolge, Locale oder Zufall (getestet inkl. Spy auf `Date.now`/`Math.random` und einem unabhängigen Orakel, das für n = 4 alle erlaubten Permutationen aufzählt). `orderingComparisonMatchesOrder` prüft ein gespeichertes Ergebnis auf innere Konsistenz gegen die gespeicherte Abgabe — ohne die Referenz zu brauchen.
Fehlerkodes (Wire, ohne Inhalte): `ORDERING_INVALID`, `_CONFIG_INVALID`, `_CONFIG_STALE`, `_STATE_INVALID`, `_ROUND_CLOSED`, `_NOT_CLOSED`, `_STALE_SUBMISSION`, `_ALREADY_COMPARED`, `_NOT_FOUND`, `_REFERENCE_MISSING`, `_REFERENCE_INVALID`, `_REFERENCE_STALE`; in `PUBLIC_CODES` (`core/errors.ts`) aufgenommen.

## 3. Domain-Lifecycle (`apps/server/src/games/core/orderingSubmission.ts`)

Reine Funktionen über serialisierbaren Zustand; keine Mutation der Eingaben; keine Uhr, kein Zufall, kein Socket/DB, **keine Punkte, kein Ledger**. `applied`/`changed` sind Domaininformation; Exactly-once braucht später Transaktion/CAS/Receipt. Die Funktionen authentifizieren nichts: `participantId`, erwarteter Scope, `timer` und `now` kommen von der Admission-/Command-Grenze einer späteren Engine.

`OrderingRoundState` (`kind: 'ORDERING_ROUND'`, **serverprivat**): `runIndex`, `roundId`, gepinnte öffentliche Config, **`referenceRevision: string | null`** (nur das opake Label — die Referenz selbst ist nie Teil des Zustands), `status: OPEN|CLOSED`, `closedAtMs`, `records[]` (je Besitzer genau einer: `order`, `submittedAtMs`, `comparison|null`, `comparedAtMs|null`). Beim Laden werden Struktur **und** Invarianten geprüft: Permutation kanonisch unter der gepinnten Config, eindeutige Besitzer, `CLOSED` ⇔ `closedAtMs`, `submittedAtMs ≤ closedAtMs`, Vergleich nur nach dem Schließen (`comparedAtMs ≥ closedAtMs`), Vergleich und `comparedAtMs` beide oder keins, Vergleichsrevision = gepinnte Revision, innere Konsistenz (Positionen/Zähler). Beschädigte Daten → `ORDERING_STATE_INVALID`; nichts wird „repariert“, nie neu gemischt.

- `createOrderingRound({ runIndex, roundId, config, referenceRevision })`; `referenceRevision: null` = keine Referenz konfiguriert.
- `submitOrdering(state, { scope, participantId, input, timer, now })`: Reihenfolge der Prüfungen: gespeicherte Daten → Scope (`STALE_ROUND`, `ORDERING_CONFIG_STALE`, `ORDERING_REFERENCE_STALE`) → Zeit → Runde offen → Frist (`timerAcceptsInput`: Pause, Ablauf und genau der Endzeitpunkt sperren) → Duplikat (`ALREADY_ANSWERED`) → Permutation. Alles oder nichts: bei jedem Fehler bleibt der Zustand unverändert, es wird kein Slot verbraucht.
- `closeOrderingRound(state, scope, now)`: **echter Annahmelock der Runde** — danach kann niemand mehr abgeben, auch nicht ein Teilnehmer ohne Record und auch nicht, solange ein externer Timer noch läuft; eine leere Runde ist schließbar; wiederholtes Schließen ist idempotent (Zeitpunkt bleibt); `now` vor einer angenommenen Abgabe → `INVALID_TIME`.
- Status ist **abgeleitet**, nie gespeichert (`orderingStatus`): `SUBMITTED` (offen) → `LOCKED` (geschlossen) → `COMPARED` (Vergleich übernommen). Bewusst nicht `JUDGED`: ein Vergleich ist kein Richterurteil und schreibt keine Punkte; die Engine bildet ihn später auf ein Urteil ab.
- `compareOrderingSubmission(state, scope, { participantId, submissionRef, reference, now })` → `{ state, applied, changed }`: nur im geschlossenen Zustand; ohne konfigurierte Referenz/ohne Referenzargument → `ORDERING_REFERENCE_MISSING` (nie geraten); `submissionRef` (`orderingRef`: Run|Runde|Besitzer|Annahmezeit) bindet an genau diese angenommene Abgabe (`ORDERING_STALE_SUBMISSION`, fremder Besitzer `ORDERING_NOT_FOUND`); die Referenz wird unter der gepinnten Config validiert und ihre Revision muss der gepinnten entsprechen (`ORDERING_REFERENCE_STALE`); das Ergebnis wird **hier** berechnet (kein Client-`isCorrect`). Dieselbe Übernahme erneut → identischer Zustand, `applied: false, changed: false`, kein neuer Zeitpunkt. Ein abweichendes Ergebnis wird nie still überschrieben (`ORDERING_ALREADY_COMPARED`; Korrekturen gehören in den zentralen Korrekturpfad). Keine Punkte, keine Ränge.
- `orderingOutcome`: server-intern, unterscheidet **keine Abgabe** / **nicht geprüft** / **geprüft** (auch mit 0 passenden Positionen). Ohne Vergleich ist nichts „richtig“ oder „falsch“.

**Revisions-Unveränderlichkeit.** Der Zustand pinnt nur das opake Label der Referenzrevision. Dass der *Inhalt* einer Revision unveränderlich ist, ist die Pflicht des Content-/Config-Snapshots (Master §6.3/§12.15: jede fachliche Änderung erhöht die Revision). Ein Hash der Referenz im Zustand wurde bewusst **nicht** ergänzt: bei höchstens 12! Permutationen wäre er offline brute-force-bar und würde einem Blind-Host oder jedem versehentlichen Snapshot die Lösung rekonstruierbar machen (Master §5.16; Auftrag §5).

## 4. Projektion und Secrets

`projectOrderingRound(audience, state, { revealed })` über das vorhandene `canView` (`PLAYER_PRIVATE`; `TEAM_PRIVATE` bewusst nicht): vor dem Reveal sieht **nur der Besitzer** seine Reihenfolge — nicht Partner im selben Team, nicht Host/Blind-Host/mitspielender Host-als-HOST, nicht Viewer/Display. Auch der Besitzer bekommt vor dem Reveal **keine** Vergleichsdaten, keine Revision und keinen `COMPARED`-Status (auf `LOCKED` geklemmt) — kein Korrektheitsorakel. Ein Reveal ist nur für eine **geschlossene** Runde möglich (`ORDERING_NOT_CLOSED`). Nach dem Reveal sehen alle Rollen alle Reihenfolgen samt Vergleichsfakten (auch „nicht geprüft“ bleibt als `comparison: null` erkennbar). Die Referenz ist nicht im Zustand und kann nicht aus der Projektion lecken; `projectOrderingSolution(audience, config, reference, { revealed })` liefert die richtige Ordnung **nur** nach explizitem Reveal und an alle Rollen gleich — vorher niemandem (Admin-/Hostrechte sind keine Informationsrechte). Eine Vorab-Einsicht für einen nicht mitspielenden Judge ist eine spätere Engine-Entscheidung (Informationsrolle). Ein mitspielender Host muss von der Engine als PLAYER projiziert werden. Es ist eine **Domainprojektion**; sie beweist keinen Socket-/Rejoin-/Recovery-Weg. Ein `revealed`-Flag beweist keine fertige Engine-Phase.

## 5. Komponente `OrderingForm` (`apps/web/src/components/OrderingForm.tsx`)

Keine Socket-/Sessionverwaltung. Props: `title?`, `config` (öffentlich, streng geprüft: ein Objekt mit Zusatzschlüsseln wie `sortValue`/`reference`/`solution` wird **nicht** gerendert), `contextKey`, `onSubmit(order, attemptId)`, `feedback?`, `disabled?`, `submitLabel?`.

**Bedienung.** Vollständige Liste in der vom Aufrufer gelieferten Startreihenfolge; je Item zwei echte Buttons „nach oben“/„nach unten“ (`type="button"`, 44 × 44 px, Tastatur und Touch), Positionsanzeige (1…n), zugängliche Namen `„<Label> nach oben, Position 2 von 4“` (doppelte Labels bleiben über die Position unterscheidbar). Kein Wrap-around: am Rand bleibt der Button fokussierbar (`aria-disabled`), tut nichts und kündigt es an. Der Fokus bleibt auf dem benutzten Button (nach dem Umhängen des Knotens wird er defensiv wiederhergestellt; in Chromium behält der Browser ihn ohnehin — die Wiederherstellung ist nicht als notwendig belegt). Live-Ansage der neuen Position (`aria-live`, nur Position, kein Lösungshinweis). Umordnen sendet nie etwas; nur der explizite „Abgeben“-Button (`type="submit"`) sendet **eine** vollständige Reihenfolge; Enter/Space auf einem Move-Button verschiebt genau einmal und sendet nicht. Die unveränderte Startreihenfolge ist eine gültige Abgabe. Nach dem Absenden wandert der Fokus auf die Statuszeile (nicht in einem deaktivierten Button stecken lassen). Drag & Drop ist bewusst nicht Teil dieses Pakets.

**Attempt-/Echo-Vertrag** (unverändert aus N1-R1/N2-R1/R2, `OrderingFeedback.attemptId` ist Pflicht): Sperre ab gültigem Submit (auch vor spätem `PENDING`); nur anwendbares Feedback zählt (aktueller `contextKey`; `LOCKED` mit null/fehlendem/aktuellem Echo, sonst Echo des aktuellen Versuchs bzw. kein offener Versuch); fremde Runde/älterer Versuch ändern weder Entwurf noch gehaltenen Zustand, Fehler, Bestätigung oder Sperre — in **jedem** Zustand, auch nachdem `LOCKED` gehalten wird; identischer Fehler als neues Objekt ist keine Antwort, derselbe Fehler mit neuem Echo schon; `null`/fehlend/fremd entsperrt nie; `LOCKED` ist endgültig; nur der Kontextwechsel setzt zurück (auch die bestätigte Reihenfolge). **Bestätigte Reihenfolge getrennt vom Status** (`accepted`): nur anwendbares `SUBMITTED`/`LOCKED` mit `order` setzt sie; eine Sperrmeldung ohne `order` löscht nichts; ohne bestätigte Reihenfolge zeigt Lock den Entwurf schreibgeschützt; weicht die bestätigte vom Entwurf ab, wird sie angezeigt. Eine bestätigte Reihenfolge, die keine gültige Permutation *dieser* Itemmenge ist, wird nicht angezeigt und nicht gehalten. Retryable Error erhält den Entwurf und erlaubt manuellen Retry (nie automatisch); fatal/Pending/Submitted/Locked sperren Moves und Senden; `disabled` bleibt erhalten. UI-`attemptId` ist **keine** serverseitige `commandId`: bei `RATE_LIMITED`/ungewissem Ausgang muss der spätere Intentclient die Command-Absicht erhalten.

**Identität/Kontext.** Der Entwurf hängt an stabilen Item-IDs: er überlebt Parent-Re-Render, neue gleichwertige Props, Labeländerung, Theme-/Akzentwechsel und reine Metadaten-Umordnung derselben IDs (Anzeige folgt den Labels der aktuellen Config, die Reihenfolge dem Entwurf). **Eine geänderte Itemmenge unter demselben `contextKey` ist ein Aufruferfehler**: die Liste wird nicht gerendert, es erscheint „Die Aufgabe hat sich geändert. Bitte lade die Seite neu.“, nichts wird in einen alten Entwurf oder eine alte Bestätigung gemischt, Senden ist gesperrt. Der Aufrufer muss `contextKey` zusammen mit der Itemmenge ändern; das setzt Entwurf, Versuch, Status und bestätigte Reihenfolge zurück.

Layout: nur Midnight-Tokens (Hell/Dunkel, sechs Akzente, Status semantisch getrennt), Itemtexte umbrechen, Touchflächen ≥ 44 px, sichtbarer Fokusring.

## 6. Trennung Vergleich und Punkte

N3 schreibt nirgends Punkte, Ledger-Einträge, Ränge, Gewinner oder Result-Daten. `matchedPositions` hat keine globale fachliche Bedeutung; ob und wie Teilwertung, Bonus, Zeitwertung oder Tie-Behandlung zählen, entscheidet eine bestätigte Engine-Regel (`decisions.md`). Bewertung/Punkte laufen später über die zentralen Ledger-/Result-Pfade mit CAS/Receipt.

## 7. Spätere Engine-Anbindung (Reihenfolge verbindlich)

1. Öffentliche Itemmetadaten und **getrennte** private Referenz → 2. Content-/Config-Snapshot mit Version/Revision (Referenzinhalt je Revision unveränderlich) → 3. serverseitig feste Präsentationsreihenfolge (`shuffleServer` nur bei der Vorbereitung, Ergebnis persistieren; beim Rejoin nie neu mischen; IDs opak, Startreihenfolge nicht zufällig korrekt) → 4. Auth/Admission/Rechte/Phase/Owner/Run/Runde/Version → 5. vorhandene frühe Request-Gates/Action-Limits/Intent/Receipt (Command-ID bei `RATE_LIMITED` erhalten) → 6. Permutationsvalidierung (`submitOrdering`) → 7. atomarer State-/Event-Commit per CAS → 8. erlaubte Projektion je Rolle (`projectOrderingRound`) → 9. tatsächlicher Rundenschluss (`closeOrderingRound`, auch bei Timerablauf/Phasenende) → 10. deterministischer Vergleich (`compareOrderingSubmission`) → 11. autorisierte Freigabe/Bewertung/Punkte über die zentralen Ledger-/Result-Pfade. Der spätere echte Verbraucher muss Socket-/DB-/Serverrestart-/Rejoin-/Recovery-/Secret-/Browsernachweise führen; „SDK-Replay vorhanden“ ist kein Recovery-Nachweis.

## 8. N1-Anzeigekorrektur (eigener Commit `b72ac34`)

`NumberField` las den angezeigten bestätigten Wert aus der gehaltenen Rückmeldung; eine gültige `LOCKED`-Meldung ohne `value` ersetzte sie, und es erschien wieder der lokale Entwurf. Jetzt hält die Sitzung den zuletzt bestätigten `NumericValue` getrennt (`confirmed`): nur anwendbares `SUBMITTED`/`LOCKED` mit `value` setzt ihn, eine Meldung ohne `value` löscht ihn nicht, fremder Kontext/älterer Versuch setzt ihn nie, nur der Kontextwechsel setzt ihn zurück, ohne bestätigten Wert zeigt Lock den Entwurf. Schnittstelle und alle R1-Tests unverändert; keine Änderung an Numerik/Toleranz/Scoring. Das macht N1 nicht zu einem integrierten Zahlen-Spielcore. Details und Nachweis: `docs/implementation/n1-numeric-foundation/review.md`.
